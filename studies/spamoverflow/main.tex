\section{Brief}

Design a service for scanning and filtering spam/malicious emails.
Specially the service needs to support:
\begin{itemize}
    \item Scanning an email via an API request.
    \item Providing access to a specified REST API, e.g. for use by front-end interfaces and internal teams.
    \item Remaining responsive while scanning emails.
    \item Being available when called, as an important email infrastructure service.
\end{itemize}

\paragraph{Task}
You are working for SpamOverflow, a new competitor in the email security space.
Spam\-Overflow uses a microservices based architecture to implement their new malicious email filtering platform.
The CEO saw on your resume that you are taking Software Architecture
and has assigned you to design and implement a service.
This service must be scalable to cope with a large influx of emails.

\paragraph{Requirements}
Email filtering software can filter email as it arrives or after.
SpamOverflow will implement a service that does not impede the flow of traffic
(i.e. does not prevent email from arriving).
It will receive an API call when the mail server receives an email message.
The service then pulls the email from the user's inbox, as fast as it can,
to prevent the user from seeing the malicious email or clicking any links.

Commercial email providers send an API request for each email received.
For optimal performance this service needs to be able to handle a large number of requests in a short period of time.

Since these emails can be dangerous, the service must be able to report that it is bad or good in a timely manner.
Though genuine emails that are incorrectly marked as dangerous should be returned to the user as quickly as possible.

Persistence is an important characteristic of the platform.
Customers will want to analyse why emails were flagged after the fact.
Upon receiving an email scan request, and after filtering,
the system must guarantee that the data has been saved to persistent storage before returning a success response.

\teacher{
    \subsection{What are the key requirements introduced by the quality scenarios?}

    \begin{itemize}
        \item Q1 \& Q2 are simple and predictable loads for the system to manage.
        \item Q3 introduces loads that requiring scaling up and down.
        \item Q4 adds the need for prioritisation, requiring some form of priority queue.
        \item Q5 implies that some malicious email will be very similar to other malicious messages.
        \item Q6 forces processing through the SpamHammer processing bottleneck.
    \end{itemize}
}
\teacher{
    \subsection{What strategies can you implement to support these scenarios?}

    \paragraph{Spam Identification}
    The \link{SpamHammer documentation}{https://github.com/CSSE6400/SpamHammer},
    shows the expected runtime and memory usage of checking if an email message is potentially malicious.
    We can see that the process is CPU intensive but light on memory,
    taking up to several seconds to process a message.
    Running this process sequentially will only work for light loads.

    \textcolor{purple}{\textbf{+ Queue malicious email checks to offload processing.}}
}
\teacher{
    \paragraph{High Value Customers}
    The scenario only mentions one priority customer,
    but the \texttt{POST /customers/{customer\_id}/emails} endpoint
    implies there could be multiple priority customers.

    \begin{itemize}
        \item Simple approach is to have two queues, one for priority processing and one for normal processing.
              Load balancing should be done separately for each queue.
              Does not allow management of a specific high value customer's priority.
        \item Separate queues for each high value customer quickly becomes unwieldy.
              Requires reconfiguring infrastructure as new high value customers are added.
        \item Could suggest redesigning the customer IDs to allow identification of each high value customer.
              If their identity is coded simply into the customer ID,
              a hash table could be created with each bucket being a message queue.
              A smart load balancer could then manage worker scaling
              to meet the performance specified in service level agreements.
    \end{itemize}

    \textcolor{purple}{\textbf{+ Two queues for simplicity.}}
}
\teacher{
    \paragraph{Leaked Directory}
    Some malicious email will be generated in bulk and will be very similar to each other.
    Once one of these messages are identified as being malicious,
    it is possible to use pattern matching to look for similar messages.
    This could be faster than waiting for a response from SpamHammer for every message.

    \begin{itemize}
        \item Need a mechanism to identify many similar malicious emails are being received.
              Potentially track number malicious emails identified as begin sent
              to a single domain over a short time period.
              Try using pattern matching or similarity metrics to check other emails sent to the same domain.
    \end{itemize}

    \textcolor{purple}{\textbf{+ Similarity metrics and observer process.}}
}
\teacher{
    \paragraph{Generating Reports}
    Creating reports on demand, once there is a large collection of data, will be resource intensive.
    Maintain tables of the report data that are updated as emails are processed.

    \textcolor{purple}{\textbf{+ Report data tables.}}
}

\section{Quality Scenarios}\label{sec:scenarios}

\paragraph{Q1: Steady Stream}
Steady receipt of email messages at a rate of \emph{M} per minute, fairly evenly spread across all customers.
Approximately 20\% of the messages are malicious.

\paragraph{Q2: Bad `News' Stream}
Steady receipt of email messages at a rate of \emph{N} per minute, fairly evenly spread across all customers.
Approximately 80\% of the messages are malicious.

\paragraph{Q3: Peaks and Troughs}
Periods of receipt of a high volume of email messages, followed by periods of low volume.

\paragraph{Q4: High Value Customer}
The Department of Defence (DoD) has adopted SpamOverflow.
They are a high value customer and you must ensure that their requests are handled quickly.
All other customers have a service level agreement (SLA) that guarantees a certain level of responsiveness.
You cannot ignore their requests to only prioritise the DoD's requests.

\paragraph{Q5: Leaked Directory}
A bad actor has managed to get the email addresses of all employees of <Large Company>.
They have sent a phishing email to all of the users advertising a pay raise with a link to a fake login page.
The email is sent to all 10,000 employees at the same time.

\paragraph{Q6: Personalised Attack}
A bad actor has trained an AI model using social media profiles of targeted victims.
They can generate personalised phishing email messages based on personal information.
As the messages are personalised, they can be of greatly different lengths and contain different content.
These messages can only be identified by SpamHammer.
They have sent these phishing messages to 2,000 users at the same time.
